Date: 2026-11-21

## 1. Decision context

The owner selected GitHub Actions as the platform for controlled recovery and validation of a disposable SQLite staging dataset. The long-term Canonical Data storage location and ownership are deferred until staging has passed review.

Controlling architecture decision: `docs/decisions/T0_GITHUB_ACTIONS_SQLITE_STAGING_RECOVERY_DECISION_2026-11-21.md`.

This document is a workflow design proposal only. It does not create or modify a workflow, initiate a run, access archive objects, create files outside GitHub documentation, or access SQLite.

## 2. Objectives and non-objectives

### Objectives

- Produce a reproducible, evidence-backed candidate dataset labeled `RECONSTRUCTED — PARTIAL COVERAGE`.
- Use an ephemeral GitHub-hosted runner as the temporary execution environment, not as durable Canonical storage.
- Preserve source-object provenance, exact source SHA, workflow/run/job identity, checksums, data coverage, gaps, SQLite schema and validation evidence.
- Fail closed on any missing source, checksum mismatch, malformed data, unsafe path, byte-cap breach, schema mismatch or validation discrepancy.
- Keep staging isolated from all existing/operational T0 assets.

### Explicit non-objectives

- Recover the former Canonical SQLite: **OLD CANONICAL = LOST**. A future archive-derived database is a different asset.
- Declare the reconstructed dataset complete or official.
- Select permanent Canonical storage, perform promotion/cutover, or start any runtime.
- Connect T1/T2, Feeder, Scheduler, API, PostgreSQL/TimescaleDB, exchange credentials or trading.
- Automatically delete source data or staging artifacts.

## 4. Proposed workflow topology

Proposed future path: `.github/workflows/t0-reconstructed-sqlite-staging.yml`  
Trigger: `workflow_dispatch` only. No push, pull_request, schedule, workflow_run or reusable-workflow trigger.

The workflow must be created only after separate owner approval. It must not be created as part of this design task.

### 4.1 Dispatch contract

Required inputs should be explicit and narrow:
- `mode`: `preflight_only` or `full_staging`.
- `workflow_approval_record_sha`: exact commit SHA containing approval to create/run this workflow.
- `preflight_run_approval_record_sha`: required only for `preflight_only`.
- `archive_materialization_approval_record_sha`: required for `full_staging`.
- `sqlite_build_approval_record_sha`: required for `full_staging`.
- `validation_artifact_approval_record_sha`: required for `full_staging`.
- `inventory_blob_sha`: exact approved 404-object inventory blob SHA.
- `importer_source_sha` and dependency-lock hashes: required for `full_staging`.
- `run_id`: owner-supplied unique immutable run identifier.
- `include_rest_tail`: default false; true is rejected unless a separate payload-transfer approval and exact payload manifest are supplied.

Approval records for each full-staging operation must already exist and be verified before the job starts. A prior preflight run is advisory only: every `full_staging` run repeats the preflight on its own runner before any source request or write. The runner is ephemeral; no temporary path is expected to persist between workflow runs.

The workflow must reject:
- any ref other than `refs/heads/main`;
- any missing or malformed SHA/run identifier;
- any missing phase-specific owner approval or approval that does not match the exact source, destination, inventory, importer and limits;
- a changed inventory blob or unexpected object key;
- `include_rest_tail=true` without the separate payload approval and verified payload hashes.

Dispatch inputs are assertions, not proof of approval. The job must fetch and verify the referenced committed decision record and exact blob identity. A typed input such as `approved=true` is not sufficient authorization.

### 4.2 Execution shape

Use one job on one GitHub-hosted runner for the entire `full_staging` invocation: preflight, source acquisition, normalization, SQLite construction, read-only validation and evidence packaging. This keeps every gate and all intermediate files in the same ephemeral filesystem and avoids passing raw data between jobs through artifacts.

A `preflight_only` invocation is a separate, read-only run. Its report does not reserve the runner, filesystem or path for a later run. The later `full_staging` invocation must repeat all preflight checks before any network request or write.

Do not split materialization and SQLite construction into separate jobs or separate workflow runs unless a new design explicitly defines secure, hash-verified artifact handoff, retention and approval gates. Separate runs use separate ephemeral runners and cannot see prior `RUNNER_TEMP` files.

- Runner: pinned supported image, initially `ubuntu-24.04`; record actual image/OS/kernel/architecture and filesystem identity at runtime.
- Job timeout: bounded; proposed maximum 30 minutes for the 404-object batch, subject to a dry-run performance estimate before implementation.
- Concurrency: one active run per staging workflow; do not cancel an in-progress data operation automatically.
- Checkout: immutable `github.sha`, shallow, `persist-credentials: false`; verify `git rev-parse HEAD == GITHUB_SHA`.
- Actions: pin every third-party action to a reviewed full commit SHA. No floating tags.
- Permissions: `contents: read` only. No repository write, deployments, packages, id-token, pull-request or issue permissions.
- No secrets or exchange credentials.
- No self-hosted runner, persistent volume, Canonical mount, VPS access, Dropbox mount or shared cache containing market data.

A GitHub-hosted runner has outbound network capability by default. YAML alone does not prove egress isolation. The `preflight_only` mode must not make network requests. In `full_staging`, the same-run preflight must complete before the source-transfer step; that step must constrain its own code to the exact allowlisted public object URLs and document that runner-level network isolation is not guaranteed by this design.

## 5. Phase gates

Every phase is separately authorized. Passing an earlier gate does not authorize a later phase.

### Gate 0 — workflow implementation approval

Required before creating the YAML:
- owner approves the exact workflow path, dispatch inputs, action SHAs, runner image, permissions, concurrency, timeout, artifact retention and phase separation;
- owner approves the exact source inventory blob and importer/validator source identity for the proposed implementation;
- workflow static review confirms no write permission, secrets, auto-trigger or Canonical mount.

Result if approved: workflow may be created, but no data operation is implied.

### Gate 1 — runner preflight

For `mode=preflight_only`, purpose is to prove the GitHub-hosted runner environment is suitable without data access. For `mode=full_staging`, the exact same checks run again as the first step in the same job, before any network request or write.

Preflight must not download, resolve, list or contact Binance objects and must not create a database.

Checks:
1. Exact triggering SHA and checked-out SHA match.
2. Runner OS/image/architecture/kernel and available tools recorded.
3. `RUNNER_TEMP` canonical path, mount point, filesystem type/device, mount options, owner, mode, free bytes and free inodes recorded.
4. Every existing path component checked with `lstat`/no-follow semantics; reject symlinks and path substitution.
5. A fresh unique run directory is proven absent before use. No target is adopted or overwritten.
6. Available space is sufficient for the approved maximum transfer plus raw archives, extraction/normalization workspace, SQLite, reports, artifact packaging and safety reserve. Estimate from measured source bytes; do not assume the 100 MiB response cap equals total disk requirement.
7. Artifact upload capability and repository artifact retention policy are documented; artifact expiry is not treated as durable storage.
8. No secrets, Canonical DB, operational T0 path or persistent mount is present in the job configuration.

Preflight is read-only: do not `mkdir`, `touch`, write-test, download, list bucket contents, resolve object URLs, or open SQLite. If any condition is failed or unverified, mark **BLOCKED** and stop. Do not select another destination automatically.

### Gate 2 — source acquisition and raw preservation

In `full_staging` mode, this gate runs only after the same-run preflight has passed and the job has verified a separate explicit owner approval naming GitHub-hosted runner temporary staging as the destination, the exact 404-key allowlist revision, source, byte ceiling, retry policy and retention/output behavior.

- Fetch only the 404 exact allowlisted object keys (202 ZIP + 202 sidecars); no bucket listing, wildcard discovery, REST tail call, fallback object, or additional date.
- Enforce cumulative response-body cap of 104,857,600 bytes across all objects and all attempts, counting partial/error response bodies and retries. Count chunks before writing; abort before a chunk would exceed the cap. Do not trust Content-Length as the enforcement mechanism.
- Bounded concurrency, connect/read timeouts and bounded retries. Retry budget and backoff must be fixed in the approved configuration. No retry that resets the byte counter.
- Use exclusive create/no-follow file creation; reject existing files, symlinks and unexpected directory entries. Never overwrite.
- Preserve exact response bytes. Record per-attempt and cumulative bytes, status, retrieval time, object key, expected/measured size, SHA-256 and file identity.
- Verify each ZIP against the committed expected size and SHA-256; verify CRC, exactly one CSV member and strict 12-column contract.
- Enforce approved per-object and aggregate uncompressed-byte limits and a maximum compression-ratio limit while streaming extraction. These limits must be measured/selected and explicitly approved before implementation; ZIP metadata alone is not trusted. Abort and quarantine on limit breach or unexpected expansion.
- Parse each sidecar strictly and compare its asserted digest with the paired ZIP digest. Separately record sidecar raw byte size and SHA-256.
- Enforce exact allowlist cardinality: 202 ZIP + 202 sidecars = 404. Any missing, extra, duplicate, malformed or mismatched object quarantines the entire run.
- The historical 11,277-byte discrepancy remains documented; recompute new aggregates from the fresh 404 measured objects without changing the historical report.

The existing historical payload validation report is not a substitute for fresh materialization evidence. A successful new retrieval is required to prove bytes staged in this runner.

### Gate 3 — normalization and source reconciliation

In `full_staging` mode, this gate runs after Gate 2 and requires explicit owner approval of the importer source SHA, dependency lock hashes, schema mapping, coverage acceptance, gap policy and `available_at_ms` semantics.

- Parse the exact Binance USD-M 12-column order. Header recognition must be exact; no heuristic header detection.
- Parse timestamps/trade counts as integers and decimal fields with exact decimal arithmetic; never convert through binary float.
- Validate timeframe alignment, UTC open/close timestamps, close-time relation, finite numeric values, OHLC envelope, non-negative volumes and taker-buy volume bounds.
- Preserve original ZIP/CSV bytes and a machine-readable mapping/disposition for all 12 source columns. Do not silently discard source-only fields.
- Canonical identity: exchange + market_type + symbol + timeframe + open_time_ms.
- Identical duplicate identity/payload may be deduplicated only with explicit multi-source provenance. Conflicting values for one identity quarantine the full candidate.
- Independently enumerate the expected M15/H1 UTC grids and report missing, extra, duplicate and conflicting identities. No interpolation, forward-fill, synthetic candle or silent omission.
- Record observed coverage boundaries separately from internal continuity. Never label earliest-ever history or post-cutoff tail complete.

**Blocking semantic decision:** archive historical first-observation times are not known. Do not set `available_at_ms` to candle close time or fabricate a historical timestamp. The owner must approve a deterministic, contract-compatible import/first-observation policy before implementation. Until then, SQLite build is BLOCKED.

### Gate 4 — disposable SQLite build

In `full_staging` mode, this gate runs in the same job after Gate 3 and requires a separate explicit owner approval naming:
- exact importer commit SHA and dependency lock hashes;
- exact schema contract and destination file path;
- exact normalized dataset manifest hash;
- `available_at_ms` policy;
- expected rows, bounds and gap acceptance;
- explicit permission to create and write one new disposable SQLite file in the runner's run directory.

Requirements:
- New unique run directory and DB path only; fail if path exists.
- Candle Contract 1.1.0 and SQLite `user_version=1`, subject to final owner confirmation of exact table/column/index/constraint definitions.
- No migration, schema extension, feeder, writer, lease activation, scheduler, API runtime or T1/T2 access.
- Deterministic import ordering by timeframe then open_time; bounded transactions; uniqueness constraints enforced.
- On any exception, mark the run QUARANTINED; do not reuse or overwrite the failed DB path.

### Gate 5 — read-only SQLite validation

In `full_staging` mode, after import commits and all writer connections are closed:
- `PRAGMA integrity_check` must return exactly `ok`.
- Verify `user_version`, exact schema, indexes, constraints and primary key.
- Independently query counts and min/max open times for each timeframe.
- Recompute timestamp alignment, expected grids, gaps, duplicates, OHLCV checks and `available_at_ms` semantics from the database.
- Compare every database candle with normalized source records and provenance mapping.
- Expected archive-only counts: M15 241,440; H1 60,360.
- If REST tail is separately approved, verify the exact payload bytes/hashes and use a separately approved expected-count manifest; candidate arithmetic totals 241,568 / 60,392 must not be treated as expected until source-level reconciliation passes.
- Any mismatch, unavailable check, schema drift or unaccounted row means **QUARANTINED / NOT PASS**.

Validation code must open the staging DB read-only (SQLite URI `mode=ro` or equivalent), and must not mutate it.

### Gate 6 — evidence artifact and owner acceptance

In `full_staging` mode, generate one run evidence bundle containing:
- workflow run URL/ID, job ID, event, triggering SHA and checked-out SHA;
- all source, importer, validator, workflow and dependency-lock blob SHAs;
- approval-record commit/blob SHAs and inventory blob SHA;
- runner metadata and preflight report;
- exact 404-object manifest with measured size/hash and sidecar raw hashes;
- per-object validation output, row counts, header mode and quarantine records;
- normalized dataset manifest, source-to-row provenance, complete gap/duplicate/conflict report;
- SQLite schema fingerprint, `user_version`, row counts, bounds, integrity-check output, DB byte size and SHA-256;
- tool versions, deterministic configuration and timestamps;
- explicit limitations and status.

Upload only after validation, as a named GitHub Actions artifact with the shortest practical retention (proposed 7 days; owner must approve). The artifact is temporary review evidence, not the sole copy of source data or Canonical storage. Record the artifact ID, digest, size and expiry. If artifact upload fails, staging acceptance is **BLOCKED** even if local checks passed.

Owner review may accept the result only as:

**STAGED / VALIDATED — RECONSTRUCTED — PARTIAL COVERAGE**

It must never be labeled recovered old Canonical, COMPLETE, OFFICIAL, or operational Canonical.

## 6. Fail-closed and quarantine behavior

Any failed or unverifiable gate stops all later phases. No fallback or auto-retry beyond the approved bounded policy.

Quarantine triggers include:
- wrong workflow ref/SHA or approval/inventory mismatch;
- unsafe runner filesystem/path or insufficient capacity;
- missing/extra object or source key;
- byte-cap breach, timeout exhaustion or repeated transport failure;
- size/hash/sidecar/CRC/CSV/schema mismatch;
- malformed timestamp/numeric value, duplicate conflict or gap-policy violation;
- importer crash, DB schema mismatch, row-count mismatch or failed integrity check;
- incomplete evidence or failed artifact upload.

Quarantine means mark the run as unusable, preserve the failure report, and prevent promotion. Do not automatically delete files, retry from scratch, vacuum, overwrite or reuse the run directory. Retention/deletion requires a separate owner decision.

## 7. Artifact and data handling policy

- Do not commit ZIP, CSV, JSON candle payloads, SQLite DB, WAL/SHM or large market-data artifacts into Git.
- Do not use Git LFS or repository Releases as an implicit Canonical store.

- No Dropbox upload, VPS copy, restore, replication or promotion in this design.
- Permanent Canonical storage, ownership, backup/restore and operational lifecycle remain deferred until after owner review.

## 12. Owner resolution addendum — 2026-11-21

**Disposition: DESIGN APPROVED WITH IMPLEMENTATION GATES. Workflow creation remains NOT AUTHORIZED.**

This addendum resolves the two open design choices in Sections 3, 5 and 9. It supersedes conflicting statements that require Candle Contract 1.1.0 semantics or leave the initial REST-tail scope undecided.

### 12.1 available_at_ms — archive rows use BAR_CLOSE_BOUNDARY

The archive does not contain trustworthy historical first-observation timestamps. Therefore:

- Archive-derived candles MUST use availability_kind=BAR_CLOSE_BOUNDARY.
- available_at_ms MUST equal the exclusive bar-close boundary: open_time_ms + timeframe_interval_ms.
- Validate the Binance CSV inclusive close timestamp first: source_close_time_ms == open_time_ms + interval_ms - 1; derive the exclusive boundary by adding exactly 1 ms. The archive fixture must confirm this source convention before parser freeze.
- This value means the bar became complete at its close boundary. It MUST NOT be described as the time the system first observed or retrieved the historical candle.
- Archive rows MUST carry immutable reconstruction provenance linking the row to the exact archive object, ZIP SHA-256, sidecar evidence, CSV member and row ordinal. Unknown/missing kind or provenance fails closed.
- Live Feeder rows retain FIRST_OBSERVED and the actual recorded observation timestamp. Do not rewrite or infer historical first-observation values.

This decision adopts the already recorded Contract 1.2.0 option B semantic split: FIRST_OBSERVED for live Feeder data and BAR_CLOSE_BOUNDARY for archive reconstruction. Contract 1.1.0 cannot truthfully represent archive rows and MUST NOT be used as the staging schema/API contract for this reconstructed dataset.

**Staging target contract:** Candle Contract 1.2.0 design, SQLite user_version=2, with required availability_kind enum and the validation/source rules in docs/design/T0_CANDLE_CONTRACT_1_2_0_DESIGN_2026-11-21.md. This is a target design only; no schema or application implementation is authorized by this addendum. Contract 1.2.0's separate fixture, implementation, compatibility and test gates remain mandatory. In particular, the exact Binance CSV header/order/encoding/close-time convention remains NOT VERIFIED until a representative fixture is separately approved and supplied.

The API freshness rule remains: BAR_CLOSE_BOUNDARY is not a live observation; it MUST NOT produce an observation age or be treated as fresh/evaluable for real-time strategy decisions. Legacy 1.1.0 consumers must not be given archive rows under relabeled FIRST_OBSERVED semantics.

### 12.2 REST tail — excluded from initial staging

The initial workflow scope is **ARCHIVE-ONLY**:

- Include exactly the 404 allowlisted archive objects: 202 ZIP + 202 paired .CHECKSUM sidecars.
- Do not retrieve REST data, call Binance REST, access the personal host, transfer its files, or include REST-tail payloads in the GitHub runner.
- Set/remove the include_rest_tail dispatch input; it is not a selectable mode in this approved initial workflow. Any future REST-tail inclusion requires a new decision and a separately approved, independently verifiable payload-transfer process. No retrieval retry, alternate endpoint, proxy, route or environment is authorized.
- The recorded personal-host tail evidence remains a separate evidence source only: M15 128 closed rows (129 raw, 1 forming excluded), H1 32 closed rows (33 raw, 1 forming excluded), fixed cutoff 2026-11-20T08:02:15.852Z. Its reported hashes were not independently recomputed by repository tooling, and payload bytes are not in this repository. It is NOT part of this staging dataset.
- Expected archive-only row counts remain M15 241,440 and H1 60,360, subject to fresh source materialization and full row-level reconciliation. Do not use the candidate combined totals 241,568 / 60,392.
- Coverage label remains RECONSTRUCTED — PARTIAL COVERAGE; the archive bounds remain the only accepted bounds. Leading history before 2019-12-31 and trailing history after the archive's 2026-11-18 final candles remain NOT VERIFIED.
